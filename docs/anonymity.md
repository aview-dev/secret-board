# 익명성 설계

secret-board 의 목표는 "회사 사람만 쓸 수 있지만, 누가 썼는지는 아무도 모른다" 입니다. 이 문서는 무엇을 지키고, 어디까지 지킬 수 있는지 정리합니다. 코드를 바꿀 때 이 문서의 규칙을 어기면 안 됩니다.

## 구조

```
브라우저 ──> portal (SvelteKit BFF)       ──X 신원 전달 안 함──> backend (Go)
              └ auth.db: user, session                           └ board.db: posts, comments, votes
```

- portal 은 "로그인한 회사 사람인지" 만 확인합니다.
- backend 는 portal 만 호출할 수 있고 (`X-Portal-Secret`), 글 내용만 받습니다.
- 두 DB 는 서로 다른 프로세스, 다른 볼륨에 있습니다. board.db 가 유출되어도 작성자는 알 수 없습니다.

## 규칙

1. backend 의 어떤 테이블에도 사용자 식별자(이메일, user id, 세션 id, IP, User-Agent) 컬럼을 만들지 않는다.
2. portal 이 backend 를 호출할 때 사용자 정보를 헤더나 본문에 넣지 않는다.
3. 요청 단위 접근 로그(access log)를 남기지 않는다. 에러 로그에도 요청자 정보를 넣지 않는다.
4. 글 / 댓글의 작성 시각은 저장할 때 뭉갠다 (예: 시간 단위). 세션 갱신 시각과 대조할 수 없게 하기 위함.
5. auth.db 에는 이름, 프로필 사진, IP, User-Agent 를 저장하지 않는다 (`mapProfileToUser`, `disableIpTracking`, session create 훅). 필요 없는 정보는 모으지 않는다.
6. 본인 글 삭제는 계정이 아니라 글마다 만든 토큰으로 한다. 토큰은 사용자만 아는 복구 키에서 브라우저가 유도하고 (`HMAC(복구 키, 글마다 랜덤 nonce)`), 서버에는 nonce 와 토큰 해시만 저장한다. 서버는 복구 키를 받지 않는다.
7. 역할은 `admin` / `user` 두 가지이고 auth.db 의 `user.role` 에 저장한다. `ADMIN_EMAILS` 환경변수에 있는 계정은 항상 관리자 (강등 불가) 다. portal 은 관리자 전용 요청 (신고 글 삭제 등) 에만 관리자 여부를 backend 에 알린다. 관리자가 쓰는 일반 글에는 붙이지 않는다. 관리자가 몇 명뿐이면 그 표시가 곧 신원이기 때문이다.
8. 관리자의 사용자 관리 화면에는 이메일, 역할, 가입일만 보여준다. 마지막 로그인 시각 같은 활동 기록은 저장하지도 보여주지도 않는다. 글 작성 시각과 맞춰 볼 수 있기 때문이다.
9. 좋아요 / 싫어요는 계정당 글마다 한 표다. 중복을 막기 위해 규칙 1, 2 의 예외로 voter 해시 하나만 backend 에 보낸다.
   - voter = `HMAC(투표 키, userId:postId)` (hex). 투표 키는 `BETTER_AUTH_SECRET` 에서 유도하고 portal 밖으로 나가지 않는다 (`src/frontend/portal/src/lib/server/votes.ts`).
   - postId 가 섞여 있어 같은 사람도 글마다 voter 가 다르다. board.db 만으로는 한 사람의 표끼리 묶을 수 없다.
   - backend 는 64 글자 hex 가 아닌 voter 를 거절한다 (이메일 같은 원래 값이 실수로 저장되지 않게).
   - 투표 시각은 저장하지 않고, `votes` 테이블은 `WITHOUT ROWID` 라 누른 순서도 남지 않는다.
   - 화면에는 개수와 "내가 누른 표" 만 보여준다. 누가 눌렀는지 보여주는 화면은 만들지 않는다.

## 한계 (솔직하게)

| 경로 | 설명 |
|---|---|
| 서버 운영자 | 운영자가 코드를 바꾸면 무엇이든 기록할 수 있다. 코드를 공개해 검증 가능하게 하는 것이 최선이다. |
| 시간 대조 | 사람이 적은 시간대에 로그인한 사람이 한 명이면, 시각을 뭉개도 추측은 가능하다. |
| 문체 / 내용 | 글 내용 자체로 작성자가 드러나는 것은 시스템이 막을 수 없다. |
| Google Workspace 관리자 | "누가 이 앱에 로그인했는지" 는 볼 수 있다. 글과는 연결되지 않는다. |
| 투표 (규칙 9) | 투표 키와 auth.db 의 user id 를 함께 가진 사람 (portal 운영자) 은 모든 user id 로 해시를 다시 계산해 누가 어느 글에 무엇을 눌렀는지 알아낼 수 있다. board.db 만 유출되면 알 수 없다. 투표 키가 바뀌면 (BETTER_AUTH_SECRET 교체) 기존 표와 연결이 끊겨 한 번 더 누를 수 있다. 글 작성자는 알 수 없으므로 자기 글에도 누를 수 있다. |
| 리버스 프록시 / 네트워크 | 앞단 프록시가 접근 로그를 남기면 규칙 3 이 무력화된다. 배포 시 함께 꺼야 한다. |

## 다음 단계 (선택)

운영자도 연결할 수 없게 하려면 블라인드 서명 기반 익명 토큰 (Privacy Pass 방식) 을 도입합니다. 로그인 세션으로 서명된 토큰을 받고, 글은 세션 없이 토큰만으로 씁니다. 서버가 모든 것을 기록해도 토큰 발급과 사용을 연결할 수 없습니다.
