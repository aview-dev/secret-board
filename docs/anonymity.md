# 익명성 설계

secret-board 의 목표는 "회사 사람만 쓸 수 있지만, 누가 썼는지는 아무도 모른다" 입니다. 이 문서는 무엇을 지키고, 어디까지 지킬 수 있는지 정리합니다. 코드를 바꿀 때 이 문서의 규칙을 어기면 안 됩니다.

## 구조

```
브라우저 ──> portal (SvelteKit BFF)       ──X 신원 전달 안 함──> backend (Go)
              └ auth.db: user, session                           └ board.db: posts, comments
```

- portal 은 "로그인한 회사 사람인지" 만 확인합니다.
- backend 는 portal 만 호출할 수 있고 (`X-Portal-Secret`), 글 내용만 받습니다.
- 두 DB 는 서로 다른 프로세스, 다른 볼륨에 있습니다. board.db 가 유출되어도 작성자는 알 수 없습니다.

## 규칙

1. backend 의 어떤 테이블에도 사용자 식별자(이메일, user id, 세션 id, IP, User-Agent) 컬럼을 만들지 않는다.
2. portal 이 backend 를 호출할 때 사용자 정보를 헤더나 본문에 넣지 않는다.
3. 요청 단위 접근 로그(access log)를 남기지 않는다. 에러 로그에도 요청자 정보를 넣지 않는다.
4. 글 / 댓글의 작성 시각은 저장할 때 뭉갠다 (예: 시간 단위). 세션 갱신 시각과 대조할 수 없게 하기 위함.
5. auth.db 에는 이름과 프로필 사진을 저장하지 않는다 (`mapProfileToUser`). 필요 없는 정보는 모으지 않는다.
6. 글 수정 / 삭제가 필요하면 계정이 아니라 글마다 발급한 랜덤 토큰으로 한다. 토큰 원문은 브라우저에만 두고, 서버에는 해시만 저장한다.

## 한계 (솔직하게)

| 경로 | 설명 |
|---|---|
| 서버 운영자 | 운영자가 코드를 바꾸면 무엇이든 기록할 수 있다. 코드를 공개해 검증 가능하게 하는 것이 최선이다. |
| 시간 대조 | 사람이 적은 시간대에 로그인한 사람이 한 명이면, 시각을 뭉개도 추측은 가능하다. |
| 문체 / 내용 | 글 내용 자체로 작성자가 드러나는 것은 시스템이 막을 수 없다. |
| Google Workspace 관리자 | "누가 이 앱에 로그인했는지" 는 볼 수 있다. 글과는 연결되지 않는다. |
| 리버스 프록시 / 네트워크 | 앞단 프록시가 접근 로그를 남기면 규칙 3 이 무력화된다. 배포 시 함께 꺼야 한다. |

## 다음 단계 (선택)

운영자도 연결할 수 없게 하려면 블라인드 서명 기반 익명 토큰 (Privacy Pass 방식) 을 도입합니다. 로그인 세션으로 서명된 토큰을 받고, 글은 세션 없이 토큰만으로 씁니다. 서버가 모든 것을 기록해도 토큰 발급과 사용을 연결할 수 없습니다.
